# ADR-0003: スプライトはキャッシュに置き、生成の 4 点目とする

## ステータス

採用(2026-08-02)

## コンテキスト

一覧画面のスクラブプレビュー(docs/prd/hover-scrub-preview.md)は、アセットを
全周レンダリングしたスプライトを必要とする。PRD 草稿はこれを
`source/{category}/{title}/previews/sprite.webp` に置くとしていたが、
CONTEXT.md は「ソースから再生成可能な派生データ」をキャッシュと定義し、
生成パイプラインには「source には一切書き込まない」という原則がある
(internal/generate/runner.go)。また、スプライトを既存の「生成」に含めるか、
独立した第 2 のジョブ種別にするかという選択肢があった。

## 決定

1. スプライトは **`cache/sprites/{category}/{title}.webp`** に置く。
   source 配下には置かない。
2. 「生成」を **GLB・サムネイル・抽出メタデータ・スプライトの 4 点を
   必ずまとめて作る処理**に再定義する(CONTEXT.md 改定済み)。
   ジョブ種別は 1 つのまま、全か無かの成功判定も維持する。

## 理由

- ドメインモデルの一貫性: スプライトは .blend から決定的に再生成できる
  純粋な派生データであり、定義上キャッシュそのもの。source に置くと
  「ソース = 唯一の正しいデータ」「アプリは source に書かない」という
  2 つの原則を同時に破る
- 既存機構への相乗り: 種別ディレクトリ(glb / thumbnails / metadata)への
  追加だけで、陳腐化判定・キャッシュ削除・配信ハンドラ・一括生成が
  そのまま機能する
- 状態モデルの単純さ: 「生成済み = 4 点すべて存在」が保たれ、
  「サムネイルはあるがスプライトがない/古い」という恒久的な中間状態と
  第 2 のジョブ UI を持ち込まずに済む
- 移行コストが今はゼロに近い: 現時点の実アセットは 1 件であり、
  既存アセットのスプライト欠落は既存の一括生成(不足分のみ)で埋まる

## 影響

- キャッシュ削除でスプライトも消え、次回生成で 48 フレームを
  レンダリングし直す(1 アセットあたり数十秒〜の追加コスト)。
  レンダリングコストの保護のためにスプライトを source へ移したくなったら、
  まず本 ADR に立ち返ること
- サムネイルだけ欲しい場合でも生成は常にスプライトを作る。
  生成時間の増加が問題になった場合は、置き場所ではなく
  サンプル数・フレーム解像度の調整で対処する
- Blender 実行 1 回のレンダー数が 1 → 49 になるため、タイムアウト
  (現行 10 分)超過のリスクは生成側の設定で管理する
