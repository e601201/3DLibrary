# ADR-0005: シェイプキーのためにモディファイアーをオブジェクト単位で手動適用する

## ステータス

採用(2026-08-12)

## コンテキスト

GLB ビューワでシェイプキー(GLB ではモーフターゲット)を確認できるように
するには、まず GLB にシェイプキーが入っていなければならない。しかし
glTF エクスポータの `export_apply=True`(モディファイアー適用)は
シェイプキー出力と排他であり、従来の生成(internal/generate/generate.py)は
「モディファイアー優先・シェイプキー全捨て」だった。

両立の選択肢は 3 つあった:

1. **常に `export_apply=False`**: シェイプキーは必ず出るが、全アセットで
   モディファイアーが未適用になる。Subdivision 前提のモデルが低解像の
   GLB になり、既存のプレビュー品質が退行する
2. **ファイル単位で分岐**: シェイプキーを含む .blend だけ
   `export_apply=False` にする。シェイプキーが 1 つでもあると、その
   ファイルの全オブジェクトのモディファイアーが失われる(体は
   Subdivision・顔にシェイプキーのキャラクターで全身が低解像になる)
3. **オブジェクト単位で手動適用**: 生成スクリプトがシェイプキーを
   持たないメッシュのモディファイアーを手動適用してから
   `export_apply=False` で書き出す

## 決定

案 3 を採る。generate.py は GLB エクスポートの前に、シェイプキーを
**持たない**メッシュオブジェクトのモディファイアーを手動で適用し、
エクスポートは `export_apply=False` で行う。

- Armature モディファイアーは適用対象から除外する(エクスポータが
  スキンとして特別扱いするため。従来と同じ)
- シェイプキーとモディファイアーを**両方**持つメッシュは、モディファイアー
  未適用のままシェイプキーを優先し、警告ログを出す
- シェイプキーを 1 つも含まない .blend は従来どおり `export_apply=True` で
  書き出す。出力は手動適用と同じになるはずだが、共有メッシュや
  メッシュ以外のオブジェクトの扱いで差が出る余地を残さないため、
  失うものが無いファイルはエクスポータの経路に留める

## 理由

- 犠牲が「シェイプキーとモディファイアーの両持ち」という、Blender 自体
  でも適用が両立しない本質的制約のケースだけに最小化される
- シェイプキーを持たないアセットの出力は従来と同等に保たれる
  (プレビュー品質の退行ゼロ)
- 手動適用ループのコスト増は、生成が「1 回の Blender 起動で行う重い処理」
  と定義されている(CONTEXT.md「生成」)ため許容範囲

## 影響

- 既存の GLB キャッシュは旧形式(シェイプキーなし)のまま。移行処理は
  設けず、ユーザーの明示的な再生成で更新する(「キャッシュが source より
  古い」状態への答えは常に再生成、という既存原則に従う)
- 将来この方式をやめる場合も、全アセットの再生成が必要になる。
  エクスポート方針を変えたくなったら、まず本 ADR に立ち返ること
- 一見すると「素直に `export_apply=True` を使えばよい」と見える実装に
  なるため、generate.py からは本 ADR を参照する
